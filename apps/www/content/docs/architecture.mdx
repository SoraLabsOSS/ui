Sora UI started as a fork of [Animate UI](https://animate-ui.com) by [@imskyleen](https://x.com/imskyleen). The initial codebase, registry conventions, and copy-paste distribution model came from that project.

Since then, the architecture, registry system, component APIs, and motion primitives have been substantially redesigned. Some patterns and abstractions still trace back to the original codebase. This page documents what the project actually inherited from upstream, what is new, and how it is laid out.

## Direction

Sora UI is built around a dual-comprehension philosophy: UI components whose behavior, constraints, composition, and metadata are understandable by both humans and AI agents. It pairs an open, copy-paste registry architecture with structured metadata exposed through an [MCP server](/docs/mcp), alongside a component roadmap centered on motion-first, composable primitives.

What's different from upstream:

- **Built for humans and AI** — an MCP server delivering rich metadata (intent, accessibility constraints, motion semantics, and composition rules) so AI assistants reason accurately about components
- **Three-tier primitives** — Motion, UI, and Catalog as distinct layers of abstraction
- **Multi-primitive support** — components ported across Radix UI, Base UI, and Headless UI
- **Deeper motion system** — accessible defaults, reduced-motion support, and composable animation primitives

## What was inherited from Animate UI

Sora UI inherited the **project structure and documentation infrastructure** — not component implementations:

- Turborepo monorepo layout
- Fumadocs-based docs site architecture
- shadcn-style registry schema and copy-paste distribution model
- Registry folder conventions (`primitives/`, `demo/`, `hooks/`, `lib/`)
- `source.config.ts` and MDX content pipeline patterns

No registry component code was carried over from Animate UI. All components in `registry/primitives/` and `registry/ui/` were independently built, reimplemented, or inspired by other sources (credited per-component in `## Credits` sections where applicable).

## Monorepo structure

**Animate UI** ships one app and three packages:

```
apps/www               — docs + registry site
packages/
  eslint-config
  typescript-config
  ui
```

**Sora UI** expanded the monorepo substantially:

```
apps/
  www                  — docs + registry site (structure inherited, contents new)
  xmcp                 — MCP server (new)
packages/
  ui                   — shared utilities (extended)
  auth-ui              — better-auth UI wiring (new)
  db                   — Drizzle ORM schema + client (new)
  www-cli              — internal contributor scaffolding CLI (new)
  typescript-config    — inherited
```

## Registry structure

Animate UI's registry is organized as a flat set of primitive categories.

Sora UI restructured it into three explicit tiers:

```
registry/
  primitives/            — Motion tier (animation building blocks)
    animate/   buttons/  effects/   texts/   disclosure/
  ui/                    — UI tier (new — does not exist in Animate UI)
    base/      radix/
  demo/
  hooks/       lib/      icons/
```

The **UI tier** (`registry/ui/`) has no equivalent in Animate UI.

## Component origins

All components in the Sora registry were independently built. Where a component was inspired by or reimplemented from an external source, that source is credited in the component's doc page under `## Credits`.

None of the component implementations were copied from Animate UI.

## Self-hosting the docs site

Sora UI's documentation site keeps **sign-in sessions and bookmarks** in a Postgres database. The schema and client live in `packages/db`, built on [Drizzle ORM](https://orm.drizzle.team/) and [`postgres.js`](https://github.com/porsager/postgres.js).

<Callout>
  **You only need a database if you enable auth.** Browsing the docs, blog,
  catalog, and registry works with zero environment variables. Set
  `NEXT_PUBLIC_ENABLE_AUTH="true"` to turn on sign-in and bookmarks.
</Callout>

**Neon is the provider we recommend for self-hosting Sora UI.** It fits the way this app talks to Postgres:

- **Pooled connections at runtime.** Neon exposes a PgBouncer endpoint that accepts thousands of client connections over a small pool of real ones — ideal for a serverless deployment that opens a connection per request.
- **Direct connections for migrations.** The same project hands you a direct (unpooled) endpoint, which schema migrations need because transaction-mode pooling does not support session-level state.
- **Branching for preview deployments.** A Neon branch is an instant, copy-on-write clone of the database with its own connection string — handy for testing migrations without touching production.
- **Scale to zero.** Idle computes suspend after a few minutes, so a low-traffic docs site costs close to nothing.

### Connection strings

Neon gives you two URLs for the same database. They differ only by the `-pooler` suffix in the hostname:

| Use | Variable | Hostname |
| --- | --- | --- |
| Runtime (pooled) | `DATABASE_URL` | `ep-xxx-pooler.<region>.aws.neon.tech` |
| Migrations (direct) | `DATABASE_URL_DIRECT` | `ep-xxx.<region>.aws.neon.tech` |

Both use port `5432` and require `sslmode=require`:

```bash
DATABASE_URL="postgresql://USER:PASSWORD@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require"
DATABASE_URL_DIRECT="postgresql://USER:PASSWORD@ep-xxx.us-east-2.aws.neon.tech/neondb?sslmode=require"
```

Copy both URLs from the Neon console with the **Connect** button. Enable
**Connection pooling** for `DATABASE_URL`, then disable it for
`DATABASE_URL_DIRECT`.

The Neon CLI can pull the pooled and direct URLs as `DATABASE_URL` and
`DATABASE_URL_UNPOOLED`:

```bash
neon env pull
```

This project uses `DATABASE_URL_DIRECT` instead of Neon's
`DATABASE_URL_UNPOOLED` name, so copy the unpooled value into
`DATABASE_URL_DIRECT` in `apps/www/.env`.

### Environment variables

Set these in `apps/www/.env`:

| Variable | Required | Description |
| --- | --- | --- |
| `NEXT_PUBLIC_ENABLE_AUTH` | Yes, for auth | Set to `"true"` to enable sign-in and bookmarks |
| `DATABASE_URL` | Yes, for auth | Pooled Postgres URL used at runtime |
| `DATABASE_URL_DIRECT` | Only for migrations | Direct Postgres URL used by `drizzle-kit` |

### Applying migrations

Schema lives in `packages/db/src/schema`. Run migrations from the package root:

```bash
cd packages/db
bun run db:migrate
```

`drizzle-kit` prefers `DATABASE_URL_DIRECT` and falls back to `DATABASE_URL`. Always give it a direct connection — running migrations through a transaction-mode pooler fails in confusing ways.

Other schema commands:

```bash
bun run db:generate   # generate SQL from the schema
bun run db:push       # push schema without a migration file (dev only)
bun run db:studio     # open Drizzle Studio
```

### Using a different Postgres provider

Any Postgres provider works — the schema is plain Postgres, and the client connects with `prepare: false` so it stays compatible with transaction-mode poolers (Neon's `-pooler` endpoint, Supabase's port `6543`).

Point `DATABASE_URL` at a **pooled** endpoint and `DATABASE_URL_DIRECT` at a **direct** one, then apply the migrations above.
